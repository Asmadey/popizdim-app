# План: «Распознать запись» из трея + диаризация

Статус: план, без реализации. 2026-10-15. Факты собраны чтением кода и документации в этой сессии (без субагентов).

## Primary goal

Пользователь кликает иконку Popizdim в трее macOS, выбирает «Распознать запись» и указывает любой аудио- или видеофайл. Дальше всё как при диктовке с микрофона: звук сохраняется в Recordings, запись появляется в истории, а текст вставляется в активное поле ввода. Реплики подписаны по говорящим («Спикер 1:», «Спикер 2:»), и при локальной модели запись не покидает Mac.

## Решения (сравнение и рекомендация)

### Диаризация: локально или Hugging Face

**Вывод: диаризация полностью локальная, на Mac. Отправлять аудио в Hugging Face не нужно.** HF — это хранилище весов, а не сервис обработки: pyannote community-1 после скачивания работает офлайн.

| Вариант                                            | Приватность                 | Скорость (Apple Silicon)                                                              | Размер и зависимости                                                                                                                                               | Ключ                                               |
| -------------------------------------------------- | --------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------- |
| **A. `speakrs 0.6` с фичей `coreml` — рекомендую** | Аудио не покидает Mac       | Авторы заявляют ×300–900 к реальному времени, DER как у pyannote (проверить в фазе 1) | Rust-крейт без Python и без ONNX Runtime (фичи `coreml`/`cpu`); веса — CoreML-конверсия community-1 из `avencera/speakrs-models`, размер не опубликован (замерить) | Зеркало без gate: HF-токен, скорее всего, не нужен |
| B. `sherpa-onnx 1.13.8`                            | Локально                    | Быстро, но качество ниже (pyannote segmentation-3.0 + простая кластеризация)          | Подтягивает C++-библиотеку sherpa-onnx; веса без gate (k2-fsa)                                                                                                     | Не нужен                                           |
| C. pyannote на Python (`pyannote.audio` + PyTorch) | Локально                    | Около ×24 к реальному времени на CPU по замерам speakrs                               | Встроить Python и PyTorch в DMG — сотни МБ, хрупко                                                                                                                 | HF-токен для gated-репозитория                     |
| D. pyannoteAI API (Precision-2)                    | Файл уходит третьей стороне | Сеть и очередь                                                                        | Только HTTP                                                                                                                                                        | Отдельный ключ pyannoteAI, ~€0,10 за час           |
| E. Sortformer в `transcribe-cpp`                   | Локально                    | Быстро                                                                                | Уже слинкован, но не больше 4 спикеров, обучен на английском, GGUF в каталоге нет                                                                                  | Не нужен                                           |

Почему A: та же модель pyannote community-1, что просил пользователь, без Python, нативный CoreML и одна Rust-зависимость.

**Конфликт версий ONNX Runtime.** В проекте `ort 2.0.0-rc.12` (через `transcribe-rs`), а опциональная зависимость speakrs — `ort ^2.0.0-rc.13`. Поэтому подключать speakrs **только** с `default-features = false, features = ["coreml"]`, без ONNX-бэкендов. Фича `online` тоже выключена: веса качает наш менеджер моделей.

**Запасной вариант:** B (sherpa-onnx), если speakrs не соберётся или окажется хуже на русской речи.

### Ключ Hugging Face

- ⚠️ Токен, присланный в чат 2026-10-15, скомпрометирован. Его нужно отозвать на hf.co/settings/tokens и выпустить новый, только `read`. В код, файлы, логи и коммиты он не попадает.
- При варианте A токен, скорее всего, не нужен: зеркало `avencera/speakrs-models` открыто.
- Если понадобится (зеркало закроют или выберем официальный gated-репозиторий), хранить как остальные ключи:
  - поле `hf_token` в `CloudSettings` (`src-tauri/src/settings.rs:542`), в `Debug` через `redact` (как `openrouter_api_key`, `settings.rs:579`);
  - пустое поле → переменная окружения `HF_TOKEN` (так же работает `OPENROUTER_API_KEY`);
  - передавать только заголовком `Authorization: Bearer …`, не в URL, не в логах;
  - поле ввода в разделе настроек «Облако (MAI)» с маскированием.

### Происхождение весов

`avencera/speakrs-models` — сторонняя конверсия весов pyannote (CC-BY-4.0). Чтобы не тянуть «что угодно с HF»:

- закрепить конкретную ревизию (commit hash) и SHA-256 каждого файла в нашем каталоге моделей;
- скачивать существующим менеджером моделей, который уже проверяет sha256, в каталог моделей приложения;
- загружать через `OwnedDiarizationPipeline::from_dir(...)`, сетевую загрузку speakrs (`from_pretrained` / фича `online`) не использовать;
- атрибуцию pyannote (CC-BY-4.0) добавить в About и README.

### ffmpeg: упаковка и вызов

1. **Сначала symphonia без ffmpeg.** `symphonia 0.5.5` уже есть в `Cargo.lock` через rodio (mp3, aac, mp4/m4a/mov, flac, ogg/vorbis, wav). Добавить прямую зависимость с фичами `mkv`, `alac`, `aiff`, `caf`. Покрывает большинство аудио и видео mp4/mov с AAC.
2. **ffmpeg как запасной путь** для того, что symphonia 0.5 не декодирует: Opus (частый в mkv/webm), AC-3/E-AC-3, DTS, WMA, AMR.
   - v1: системный ffmpeg. GUI-приложение не видит `PATH` оболочки, поэтому искать по порядку: путь из настроек → `/opt/homebrew/bin/ffmpeg` → `/usr/local/bin/ffmpeg` → `PATH`. Нет ffmpeg — понятная ошибка «Формат требует ffmpeg: brew install ffmpeg».
   - v2 (по решению пользователя): встроить LGPL-сборку ffmpeg (без `--enable-gpl`) как Tauri sidecar через `bundle.externalBin` в `tauri.conf.json`. Это +~20–40 МБ к DMG и требует подписи бинарника при нотаризации.
   - Вызов: `std::process::Command` (плагина shell в проекте нет), аргументы — массивом, без оболочки: `ffmpeg -nostdin -hide_banner -loglevel error -i <file> -map 0:a:0 -vn -ac 1 -ar 16000 -f f32le -`. stdout читать потоково в `Vec<f32>`, stderr — в лог при ошибке. Отмена = `child.kill()`.

### Слияние текста и меток говорящих

**Сначала диаризация, потом транскрипция по репликам.**

1. `speakrs` → `Vec<Segment { start, end, speaker }>`.
2. Нормализация: склеить соседние сегменты одного спикера с паузой < 1 с; выбросить сегменты < 0,3 с; длинные (> 30 с) резать по паузам Silero VAD.
3. Каждый кусок → активная модель через существующий `TranscriptionManager::transcribe(Vec<f32>)` (`managers/transcription.rs:1365`). Облачные провайдеры — параллельно (как `cloud/openrouter.rs`, до 4 запросов).
4. Сборка: `[00:01:23] Спикер 1: текст`; подряд идущие реплики одного спикера объединяются в абзац.

Почему так: подход работает с **любой** активной моделью, включая облачные OpenRouter и Azure, которые не отдают таймкоды слов.
Минусы: больше запросов к облаку; на границах реплик модель теряет контекст; при перекрытии речи реплика достаётся одному спикеру.
Выключенная диаризация = тот же конвейер с нарезкой только по VAD.

### Куда выводить результат: так же, как при диктовке с микрофона

Решение пользователя (2026-10-15): файл — это просто другой источник звука. После декодирования он идёт по тому же пути, что и запись с микрофона (`src-tauri/src/actions.rs:636-800`):

1. **Recordings.** Извлечённая дорожка (16 кГц, моно, 16 бит) сохраняется функцией `save_wav_file` в `hm.recordings_dir()` как `handy-<timestamp>.wav`, параллельно с транскрипцией, как в `actions.rs:639-645`. Исходный медиафайл не копируется: в Recordings лежит только звук. Действует обычная политика хранения записей (`RecordingRetentionPeriod`). Час звука — около 115 МБ.
2. **Постобработка без LLM.** Решение пользователя (2026-10-15): LLM для файлов пока не используется вообще — ни по умолчанию, ни как опция, ни через `--toggle-post-process`. К тексту каждой реплики применяется только локальная обработка `process_transcription_output(&app, &text, false)` (`actions.rs:353`): удаление слов-паразитов, Custom Words и нормализация. Флаг `post_process` всегда `false`, в историю пишется `post_process_requested = false`.
3. **История.** `hm.save_entry(file_name, transcription, ...)`, как в `actions.rs:729`. Запись можно прослушать и повторить в истории, как обычную. Дополнительно сохраняются `source_name` (имя исходного файла) и `segments_json` (реплики).
4. **Вставка в активное поле.** `ah.run_on_main_thread(|| utils::paste(final_text, ...))`, как в `actions.rs:743-760`, с теми же настройками способа вставки и буфера обмена (`ClipboardHandling`, `PasteMethod`, `append_trailing_space`, `auto_submit`). Ошибка вставки → событие `paste-error`, текст остаётся в истории.
5. **Оверлей и трей.** Прогресс «Распознаю файл: 35%» в оверлее, `TrayIconState::Transcribing`, «Отмена» в трее. По окончании оверлей скрывается, как после диктовки.

**Возврат фокуса после диалога.** Приложение работает в режиме Accessory (`lib.rs:159`). Системный диалог выбора файла делает Popizdim активным, и после закрытия фокус не обязательно вернётся в прежнее окно. Кода для этого сейчас нет. Поэтому:

- перед открытием диалога запомнить `NSWorkspace::sharedWorkspace().frontmostApplication()` (`objc2-app-kit 0.3` уже в зависимостях);
- после выбора файла (и после отмены диалога) активировать это приложение обратно;
- в момент вставки текст попадает туда, где фокус сейчас, как при диктовке. Если пользователь за время распознавания переключился на другое окно, текст вставится туда.

v2: окно результата с переименованием спикеров и «Сохранить как» txt / md / srt.

### Anti-patterns (не делать)

- Не вызывать `blocking_pick_file()` из обработчика меню: он выполняется на главном потоке, и macOS повиснет.
- Не включать в speakrs ONNX-бэкенды и фичу `online` (конфликт `ort rc.12` / `rc.13`, неконтролируемая загрузка).
- Не тянуть Python или PyTorch.
- Не вызывать ffmpeg через `sh -c` и не склеивать аргументы в строку: имя файла может содержать пробелы и кавычки.
- Не писать HF-токен в лог, URL, `loop-state.json`, PROGRESS.md, коммиты.
- Не копировать исходный медиафайл в `recordings_dir` (видео может весить гигабайты): туда пишется только извлечённый WAV через `save_wav_file`.
- Не писать отдельный путь вывода: файл идёт через ту же цепочку `process_transcription_output` → `save_entry` → `utils::paste`, что и микрофон.
- Не вызывать `utils::paste` вне главного потока.
- Не вызывать LLM для файлов: `post_process` всегда `false`, никаких настроек и пунктов меню «с постобработкой» для файлов.
- Не добавлять Sortformer в каталог как модель транскрипции (тест `pure_diarization_models_are_not_downloadable`, `catalog/mod.rs:235`).

## Phase 1: Прототип диаризации

> **How this serves the primary goal:** подтверждает, что speakrs на CoreML собирается рядом с текущими зависимостями и правильно делит русскую речь, до того как строить на нём UI.

**Результат (2026-10-15) — `spikes/diarize-speakrs/README.md`:**

- ✅ Сборка: отдельный крейт, собран в песочнице без сети. В приложении остаётся один `ort` (rc.12).
- ✅ Скорость: ×72–105 к реальному времени на 5 минутах, загрузка моделей < 1 с.
- ✅ Веса: ревизия `67f963b6a1d94fcd4678948237b3cc8bd69bf1d8`, 68 файлов, 273 МБ, все хеши сверены (`manifest.json`). Репозиторий без gate — HF-токен не нужен.
- ⚠️ Разделение: на коротких синтетических диалогах (27–37 с) найдено 2 говорящих из 3. На 5 минутах — 3 из 3, верно 48 из 56 реплик. Порог AHC не помогает; параметра «число говорящих» нет.
- ⚠️ Память: пик 1,3–2,0 ГБ.
- ✅ Настоящая запись `agora.mp4` (14,5 мин, один человек): ×134, пик 1,7 ГБ. Порог по умолчанию дал 1 говорящего — верно; порог 0,3 ложно делит на двоих. В приложении оставляем порог speakrs по умолчанию и не даём его менять.
- ⏳ Не проверено: настоящая запись с несколькими людьми. Настройку «число говорящих» в фазе 4 не делаем, пока не увидим реальный случай слияния.

Прототип сделан отдельным крейтом в `spikes/diarize-speakrs/`, а не в `src-tauri/examples/`, чтобы не собирать всё приложение и держать чужой код в песочнице.

**Что сделать**

- Тестовые записи: 2–3 говорящих по-русски, 5–10 минут; один подкаст на английском.
- Замерить: время, ОЗУ, размер весов, число найденных спикеров, ошибки на слух. Для сравнения прогнать sherpa-onnx.

**Проверка**

- Скорость не ниже ×50 к реальному времени на M-серии, спикеры различаются правильно.
- Записать итоги в PROGRESS.md: выбранный движок, ревизию и SHA-256 весов.

**Anti-pattern guard:** если сборка требует второй `ort` — не «чинить» форками, а переходить на запасной вариант B.

## Phase 3: Транскрипция файла активной моделью и вывод как у микрофона

> **How this serves the primary goal:** превращает звук из файла в текст той моделью, которую пользователь уже выбрал, и выдаёт его тем же путём, что и диктовку: Recordings, история, вставка в активное поле.

**Результат (2026-10-16), код не закоммичен:**

- ✅ `file_transcription/chunk.rs`: Silero/Earshot VAD по настройке (`create_vad_detector` вынесен из `managers/audio.rs`), речь с полями 0,3 с, куски ≤ 25 с, длинная речь режется в самом тихом месте, тишина в модель не уходит; без VAD — нарезка по тихим местам.
- ✅ `mod.rs`: загрузка модели параллельно с декодированием, куски через `TranscriptionManager::transcribe` (слова-паразиты и Custom Words внутри), склейка `join_phrases`, затем WAV в Recordings → `save_entry` → `utils::paste` на главном потоке. LLM не используется.
- ✅ Прогресс в трее на весь процесс: декодирование 0–10 %, VAD 10–20 %, распознавание 20–100 % по длительности кусков; «Отмена» прерывает любой этап; диктовка не стартует, пока идёт файл (`start`/`stop` в `actions.rs`).

**Что сделать**

- Скопировать хвост конвейера микрофона из `actions.rs:636-800` в `file_transcription/run.rs`. Лучше вынести общую часть («сохранить WAV → постобработка → история → вставка») в функцию, которую вызывают оба источника, чтобы не дублировать проверки отмены.
- `file_transcription/run.rs`: фоновая задача (`tauri::async_runtime::spawn_blocking`):
  - параллельно с транскрипцией: `save_wav_file` извлечённой дорожки в `recordings_dir()` как `handy-<timestamp>.wav`;
